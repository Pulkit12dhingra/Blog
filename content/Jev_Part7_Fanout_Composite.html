Advanced Jev Patterns: Fan-Out and Composite Scoring

Back to Home

Once a workflow has several decisions, it is tempting to ask one question, wait for the answer, and then make another request. Jev supports a different shape: ask independent questions about the same state together, then combine their signals in code.

1. Fan out independent questions

A ticket might need a team classification, an urgency signal, and a refund-request check. These judgments use the same ticket but do not depend on each other's answer. Put them in one questions map. Jev evaluates each question independently, and your code decides which results matter for the route.

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

ticket_state = {"ticket": {"message": "The export is broken for our team, and we cannot finish today's report."}}

questions = {
        "team": Choice(
            instructions="Which team should handle the customer's primary request?",
            criteria={
                "billing": "Charges, invoices, refunds, or subscriptions",
                "technical": "Bugs, outages, or integrations",
                "account": "Login, profile, or account security",
            },
        ),
        "refund_requested": Noul(
            instructions="Does `ticket.message` explicitly request a refund or credit?",
        ),
        "severity": Score(
            instructions="How severe is the reported software issue?",
            criteria=[
                "Cosmetic issue with no impact to functionality",
                "Broken or degraded feature, but a workaround exists",
                "Blocking issue with no workaround",
            ],
        ),
        "customer_impact": Score(
            instructions="How much does this issue affect the customer's work?",
            criteria=[
                "No meaningful disruption",
                "Some work is delayed, but a workaround exists",
                "The customer cannot complete an important task",
            ],
        ),
        "urgency_level": Score(
            instructions="How soon does the customer need this issue resolved?",
            criteria=["Can wait", "Needs attention soon", "Needs attention today"],
        ),
    }

with TypeSafeClient() as client:
    response = client.system_one(state=ticket_state, questions=questions)

Speculative fan-out means including questions that may only matter on some paths. If the ticket is not about billing, code can ignore the refund result. This trades the cost of extra question tokens for fewer serial request round trips. Batching does not make questions free, and a very large state still has to be sent.

2. Know when a second request is needed

Questions can share one request when they can all be formed from the same state. A follow-up request is appropriate when code needs the first answer to fetch new data, construct a new state, or choose the next question's options. For example, a classifier that selects a branch of a taxonomy may need a second Choice after it knows which branch to inspect.

Do not serialize independent questions just because one sounds like a natural first step. Conversely, do not batch together questions that genuinely require evidence unavailable until after the first result.

3. Compose atomic scores in code

A single broad score such as “How important is this ticket?” can hide several judgments. Split it into severity, customer impact, and urgency, then define how your application combines them. The example below uses three two-point Score rubrics. Each score is normalized to the 0-to-1 interval before applying its weight.

answers = response.answers

severity = answers["severity"].score / 2
impact = answers["customer_impact"].score / 2
urgency = answers["urgency_level"].score / 2

priority = 0.50 * severity + 0.30 * impact + 0.20 * urgency

The weights are product policy, not model output. Normalization matters when the rubrics have different numbers of levels. Keep the original answers too, so the composite does not conceal a weak or conflicting component. For high-impact decisions, include confidence or probability checks before acting.

4. Make the pattern measurable

  • Compare batched and separate requests on the same test cases.
  • Measure input tokens, total latency, and outcomes rather than assuming the batching benefit.
  • Test questions individually and as part of the complete request.
  • Evaluate composite weights against labeled outcomes or reviewer decisions.
  • Keep thresholds and weights in a visible, reviewable part of the application.

The official parallel-questions cookbook reports its own measured cost and latency comparison for one document-heavy workload. Treat such results as workload-specific, not a universal performance guarantee.
