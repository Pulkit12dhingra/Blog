Build a Complete Jev Workflow: Support Ticket Triage

Back to Home

The previous articles used each primitive on its own. Now we combine them in a small support-ticket workflow: Choice identifies a team, Score rates severity, and Noul checks for an explicit refund request. Jev supplies structured judgments; Python decides whether to route the ticket or ask a person to review it.

1. Keep the workflow in code

Start with deterministic work. Validate required fields, remove irrelevant data, and apply exact rules before calling a model. Put only the context the questions need in the state. Here, all three questions use the same ticket message, so they can be sent together.

2. Define independent questions

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

QUESTIONS = {
    "team": Choice(
        instructions="Which team should handle the customer's primary request?",
        criteria={
            "billing": "Charges, invoices, refunds, or subscriptions",
            "technical": "Bugs, errors, outages, or integrations",
            "account": "Login, profile, permissions, or account security",
            "other": "A request outside the listed teams",
        },
    ),
    "refund_requested": Noul(
        instructions="Does the customer explicitly request a refund or credit?",
    ),
    "severity": Score(
        instructions="How severe is the reported software issue?",
        criteria=[
            "Cosmetic issue with no impact to functionality",
            "Broken or degraded feature, but a workaround exists",
            "Blocking issue with no workaround",
        ],
    ),
}

state = {
    "ticket": {
        "message": "I was charged twice for order A-104. Please refund the duplicate charge."
    }
}

with TypeSafeClient() as client:
    response = client.system_one(state=state, questions=QUESTIONS)

The questions are independent judgments about the same state. The answer to one is not hidden context for another. If a later question truly needs data that code can fetch only after seeing an earlier answer, make that a second request. Otherwise, ask independent questions together and let code ignore irrelevant answers.

3. Apply explicit policy to the answers

Keep confidence thresholds and business rules in ordinary code. The function below returns a routing decision without performing a real side effect. Its thresholds are examples only.

def decide(response) -> dict[str, str]:
    answers = response.answers
    team = answers["team"]
    severity = answers["severity"]
    refund_probability = answers["refund_requested"].noul

    if team.confidence < 0.65:
        return {"queue": "manual_triage", "priority": "review"}

    if severity.confidence < 0.60:
        priority = "review"
    elif severity.score >= 1.5:
        priority = "high"
    elif severity.score >= 0.5:
        priority = "normal"
    else:
        priority = "low"

    if team.choice == "billing" and refund_probability >= 0.80:
        queue = "billing_refund_review"
    elif team.choice == "billing":
        queue = "billing"
    else:
        queue = team.choice

    return {"queue": queue, "priority": priority}

This design does not equate high confidence with guaranteed correctness. It separates model judgments from product policy, so a team can tune review rules using labeled tickets and the relative cost of mistakes.

4. Evaluate the whole path

Test the workflow on a fixed set of tickets with expected team, refund, and severity labels. Review each stage separately and then check the final route. Useful cases include:

  • A clearly technical ticket with a reproducible error
  • A billing complaint that does not ask for a refund
  • A message containing both a billing issue and a technical problem
  • A vague request with insufficient information
  • A high-impact ticket where incorrect automation would be costly

Record the resolved model version, raw answers, thresholds, and final application decision. This makes it possible to tell whether an error came from question wording, an unsuitable rubric, or downstream policy.

What you have built

  • One structured state for the ticket
  • Three independent typed judgments in one request
  • Code-owned routing, severity bands, and review paths
  • A test plan for evaluating the entire decision process
