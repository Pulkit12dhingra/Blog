Noul in Practice: Detecting Refund Requests with Jev

Back to Home

A yes/no detector is useful only when “yes” and “no” have a clear meaning. This article builds a refund-request detector with Jev's Noul primitive, then uses ordinary Python to decide what to do with strong, weak, and uncertain signals.

1. When to use Noul

Use Noul when one question has two possible outcomes and the probability of “yes” is useful to your application. Examples include whether a message asks for a refund, whether a passage contains a cited fact, or whether a ticket expresses urgency.

Noul is not a general 0-to-1 rating scale. The value represents the probability that the proposition is true. If the actual task is to rate a customer from calm to angry, define ordered levels with Score instead.

2. State the proposition clearly

Consider these two support messages:

  • “I was charged twice. Please refund the duplicate charge.”
  • “I was charged twice. Can you check what happened?”

Both describe a duplicate charge, but only the first explicitly requests a refund. The Noul question should focus on the requested action, not infer it from the billing problem.

from typesafe_sdk import Noul, NoulCriteria

refund_requested = Noul(
    instructions="Does the customer explicitly request a refund or credit?",
    criteria=NoulCriteria(
        true="The customer asks for money back or an account credit.",
        false="The customer reports a billing issue but does not ask for money back or credit.",
    ),
)

The criteria are optional. Add them when the boundary is subtle, and make sure they agree with the question. Phrase the positive case so a value near 1 always means the action described in code.

3. Ask the question and read its answer

from typesafe_sdk import Noul, NoulCriteria, TypeSafeClient

question = Noul(
    instructions="Does the customer explicitly request a refund or credit?",
    criteria=NoulCriteria(
        true="The customer asks for money back or an account credit.",
        false="The customer reports a billing issue but does not ask for money back or credit.",
    ),
)

message = "I was charged twice. Please refund the duplicate charge."

with TypeSafeClient() as client:
    response = client.system_one(
        state=message,
        questions={"refund_requested": question},
    )

probability_yes = response.answers["refund_requested"].noul
print(probability_yes)

The code reads the Noul answer from the response by question ID. A real probability comes from the API. No sample output is claimed here because the result depends on the model version and question.

4. Let application policy handle uncertainty

A single threshold at 0.5 forces every message into yes or no, even when the model is unsure. For a refund workflow, the cost of issuing an incorrect refund may differ from the cost of asking a reviewer to inspect a ticket. The thresholds should reflect those costs.

YES_THRESHOLD = 0.80
NO_THRESHOLD = 0.20


def refund_route(probability_yes: float) -> str:
    if probability_yes >= YES_THRESHOLD:
        return "send_for_refund_review"
    if probability_yes <= NO_THRESHOLD:
        return "standard_billing_queue"
    return "human_review"

These numbers are example policy values, not recommended defaults. Tune them on labeled examples from your own workflow. Track false positives, false negatives, and the number of tickets sent to review.

5. Evaluate with examples, not intuition

Before automating actions, create a small evaluation set with expected labels. Include explicit requests, billing complaints without refund requests, indirect wording, and messages with multiple requests. Review errors and revise the question or criteria when the boundary is unclear.

Measure application outcomes as well as model outputs. A threshold that catches more refund requests may also route too many ordinary billing questions into the refund path. Keep the raw probability and final route in logs so reviewers can diagnose behavior.

Safety note: A high Noul probability is not a guarantee that the proposition is true. For financial actions, use approval rules and human review appropriate to the consequences.

Key takeaways

  • Use Noul for one clearly phrased yes/no proposition.
  • The returned value is probability of yes, not a measure of degree.
  • Criteria can clarify what true and false mean.
  • Thresholds and review paths belong to your application and must be evaluated on your data.
