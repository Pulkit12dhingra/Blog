What Is Jev? A Practical Introduction to System One Models

Back to Home

Many applications need a model to make a small judgment: classify a support ticket, rate its urgency, or check whether it asks for a refund. A generative model can answer these questions in text, but application code then has to interpret that text. Jev takes a different approach: you define the answer shape, ask a focused question, and receive a structured result that code can inspect.

In this series: Part 1 introduces Jev and System One. Part 2 makes a first evaluation. Parts 3, 4, and 5 focus on Noul, Score, and Choice through separate use cases. Part 6 combines them into a working workflow.

1. Jev in one sentence

Jev is TypeSafe's flagship System One model, designed to evaluate supplied content against typed questions and return structured answers. The application provides the content as a state and the questions it wants answered. Jev returns one answer for each question, in a form the application can use directly.

For example, a support application can provide a customer's message and ask whether the customer requested a refund. Jev returns a Noul value, a probability from 0 to 1 that the answer is yes. Your code decides what that value means for the workflow, such as continuing automatically, asking the customer to clarify, or sending the ticket to a person.

2. How this differs from a generative LLM

A generative LLM is built to produce text. It can explain an answer, draft a response, or produce code. Jev is built for a different job: making constrained judgments that software can consume. It does not write the customer reply, invent an action plan, or run tools by itself.

Question Generative LLM Jev
What does it return? Generated text, such as an explanation or draft response A constrained answer such as a selected option, score, or yes probability
Who controls the workflow? The application or agent interprets the response and chooses what to do Your code defines the workflow and decides how to use the answer
A good fit for Writing, summarizing, explaining, and open-ended responses Classification, scoring, detection, routing, and other bounded judgments

These tools can work together. Jev can classify a request or check evidence, while a generative LLM writes the final response. They are complementary components, not interchangeable model settings.

3. The request and answer mental model

A Jev request has three main parts: the state to evaluate, a model identifier, and a map of questions. Each question has an ID chosen by your code, a type, and instructions. The ID makes it easy to find the matching answer; it is not the question itself.

The following request shape asks whether a support message contains a refund request:

{
  "state": "I was charged twice. Please refund the duplicate charge.",
  "model": "jev-latest",
  "questions": {
    "refund_requested": {
      "type": "noul",
      "instructions": "Does the customer request a refund?"
    }
  }
}

This is an example of the documented HTTP API request format. The response includes the model that handled the request, an answers object keyed by refund_requested, and token usage. The Noul answer itself is named noul. A value near 1 is a strong yes, a value near 0 is a strong no, and a value near 0.5 indicates an uncertain judgment. The response below is illustrative, including its numeric values. A live response reports the model version and token usage for the actual request: 

{
  "model": "jev-1.13.0",
  "answers": {
    "refund_requested": {
      "type": "noul",
      "noul": 0.96
    }
  },
  "usage": {
    "input_tokens": 120,
    "output_tokens": 12
  }
}

The important boundary is that Jev evaluates the question, but your code owns the action. A threshold such as 0.8 is an application policy, not a universal value supplied by the model. Choose and test it using examples from the workflow you are building.

4. The three question types

Jev offers three core primitives. The right one depends on the shape of the answer your application needs:

  • Noul: Is a statement true? Returns the probability that the answer is yes.
  • Choice: Which option from a defined set fits best? Returns the chosen option and probabilities across the options.
  • Score: Where does the input fall on an ordered rubric? Returns a score, probabilities across the levels, and confidence.

The next articles will use each primitive in its own example. First, a Noul will detect a refund request. Then a Score will rate issue severity, and a Choice will route tickets by intent. Part 6 will combine the three in one support workflow.

5. Where Jev fits, and where it does not

Jev is useful when the application needs a natural-language judgment with a defined answer shape. It is not a replacement for exact computation or for a generative model when the product needs new prose.

Good candidates
  • Classifying messages into known categories
  • Checking whether a document contains a specified property
  • Rating content against a clearly described rubric
  • Routing uncertain cases to review
Keep these in code or another model
  • Exact arithmetic, counting, and date comparisons
  • Deterministic business rules and side effects
  • Drafting explanations or free-form customer responses
  • Tasks requiring images, audio, or video as input

The current documentation describes Jev as text-only. It also cautions against relying on Jev for exact math, counting, or date ordering. Give it only relevant state, write direct questions, and test edge cases. Model capabilities and limits can change, so check the current models page before relying on a particular capability.

6. What to remember

  1. Your application supplies the state and defines the question.
  2. Jev returns a typed answer that code can inspect.
  3. Your code owns thresholds, routing, side effects, and review paths.
  4. Use a generative model for generated language, and Jev for bounded judgments.
  5. Validate the complete workflow on representative data before deploying it.
