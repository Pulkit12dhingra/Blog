Choice in Practice: Routing Tickets by Intent with Jev

When a support ticket belongs in one of a known set of queues, Choice can classify it into that set. The result includes both the selected option and the probability distribution, so application code can route clear cases and handle ambiguity deliberately.

1. Define the destinations

Suppose a support team routes incoming messages to billing, technical support, account support, or an “other” queue. Write a description for each option that explains its boundary. The model needs to distinguish similar options from the ticket's content, not merely repeat a label.

from typesafe_sdk import Choice

team_question = Choice(
    instructions="Which team should handle the customer's primary request?",
    criteria={
        "billing": "Charges, invoices, refunds, or subscriptions",
        "technical": "Bugs, errors, outages, or integration problems",
        "account": "Login, profile, permissions, or account security",
        "other": "A request that does not fit the listed support teams",
    },
)

Choice is appropriate because these destinations are categories, not levels on a scale. Include a fallback when real tickets can fall outside the listed options. The API allows up to 255 options, but more options still require clear descriptions and evaluation.

2. Evaluate a ticket

from typesafe_sdk import Choice, TypeSafeClient

message = "My payment was taken twice for the same order."
questions = {
    "team": Choice(
        instructions="Which team should handle the customer's primary request?",
        criteria={
            "billing": "Charges, invoices, refunds, or subscriptions",
            "technical": "Bugs, errors, outages, or integration problems",
            "account": "Login, profile, permissions, or account security",
            "other": "A request that does not fit the listed support teams",
        },
    )
}

with TypeSafeClient() as client:
    response = client.system_one(state=message, questions=questions)

answer = response.answers["team"]
print(answer.choice)
print(answer.probabilities)
print(answer.confidence)

The example demonstrates SDK field access. No live classification output is included. In an application, log the result alongside the model version and the outcome of the routing policy so behavior can be evaluated later.

3. Understand the distribution

choice is the option with the highest probability. probabilities gives the distribution over every option, and confidence summarizes how concentrated that distribution is. A confident classification can still be wrong, so evaluate the complete route against labeled examples.

A Choice distribution always assigns its probability across the supplied options. That means some option will rank first even when none is a good fit. An “other” option can provide an escape route, but if the application must decide whether the content answers a question at all, pair the ranking with a separate Noul question that checks for existence or relevance.

4. Add a review path

MIN_CONFIDENCE = 0.65


def route_team(answer) -> str:
    if answer.confidence < MIN_CONFIDENCE:
        return "manual_triage"
    return answer.choice

The confidence threshold is an example, not a TypeSafe default. Set it from the cost of a wrong route, the cost of manual review, and validation results. For high-impact actions, a lower-risk design may require confirmation even when the classification is clear.

5. Make the classifier testable

Maintain labeled examples for every team and include boundary cases, such as a message that mentions both a duplicate charge and a login failure. Review not only whether the top choice is right, but also whether the probability distribution and confidence support the application's action.

  • Keep the category set aligned with the real routing destinations.
  • Write parallel, contrasting criteria for easily confused teams.
  • Use a fallback option for uncovered cases.
  • Send ambiguous or costly decisions to the appropriate review path.
