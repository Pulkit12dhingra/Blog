Score in Practice: Rating Ticket Severity with Jev

Back to Home

Some judgments are not yes/no and are not a choice among unrelated labels. Issue severity has an order: a cosmetic issue is less severe than a broken feature, which is less severe than a blocker. Score lets your application define that rubric and receive a position across its levels.

1. Define the scale in words

Imagine a ticket that says a PDF export fails in Safari, while CSV export still works for some customers. The application needs a severity estimate, but “rate severity from zero to two” does not explain what each number means. Instead, describe observable situations:

  1. Cosmetic issue with no impact to functionality
  2. Broken or degraded feature, but a workaround exists
  3. Blocking issue with no workaround

Score levels are ordered. Their position in the criteria list defines their index, beginning at zero. The model sees each description, so make the level descriptions independently understandable. Avoid “more severe than the previous level” and vague labels such as “medium.”

2. Ask the Score question

from typesafe_sdk import Score, TypeSafeClient

severity_question = Score(
    instructions="How severe is the reported software issue?",
    criteria=[
        "Cosmetic issue with no impact to functionality",
        "Broken or degraded feature, but a workaround exists",
        "Blocking issue with no workaround",
    ],
)

ticket = (
    "The PDF export button hangs in Safari. CSV export still works for some "
    "customers, but others cannot export their reports."
)

with TypeSafeClient() as client:
    response = client.system_one(
        state=ticket,
        questions={"severity": severity_question},
    )

answer = response.answers["severity"]
print(answer.score)
print(answer.probabilities)
print(answer.confidence)

This code shows how to call the SDK and inspect a Score answer. The resulting values are intentionally not shown because no live Jev evaluation was run for this article.

3. Read all three parts of the answer

  • score is a probability-weighted position across the numbered levels. It can fall between two levels.
  • probabilities shows how the answer is distributed across the levels.
  • confidence summarizes how concentrated that distribution is. It is not a guarantee that the answer is correct.

Two different probability distributions can produce the same expected score. Inspect the distribution when the distinction matters. Do not interpret a Score value as a precise physical measurement or as the percentage of cases in a category.

4. Keep the rubric about one dimension

Severity should measure severity, not severity plus customer frustration plus the quality of the bug report. When a decision depends on several independent qualities, ask one Score question per quality and combine the results in code. Part 6 will show how several question types can share one request.

Use examples in level descriptions only when they clarify real boundaries in your data. Examples should represent the intended level, not merely resemble the input by topic. Test revised criteria on examples that were not used to write them.

5. Turn a score into an application decision

A Score does not choose a queue or perform an action. Your application can define a conservative policy, for example, automatically prioritizing a high-severity result only when the confidence is sufficient, and sending ambiguous cases for review. The appropriate cutoffs depend on the consequences and on evaluation results from your own tickets.

def needs_review(answer) -> bool:
    return answer.confidence < 0.70


def severity_band(answer) -> str:
    if needs_review(answer):
        return "review"
    if answer.score >= 1.5:
        return "high"
    if answer.score >= 0.5:
        return "normal"
    return "low"

The thresholds above are illustrative policy values. Set production values using labeled examples, track error types, and adjust the policy when the review burden or mistake rate is unacceptable.

Checklist for a useful Score

  • Use Score only when the answer is an ordered spectrum.
  • Describe situations for each level, not just numeric labels.
  • Keep each rubric to one dimension.
  • Review probabilities and confidence, not only the final score.
  • Validate the rubric and action thresholds on your own data.
